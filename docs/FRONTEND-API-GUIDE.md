# מדריך API לצד הלקוח – "יחד"

המסמך הזה מיועד לך כשאת כותבת את צד ה־React. יש בו כל מה שצריך כדי להתחבר לשרת: איך שולחים כל בקשה, מה חוזר, איך קוראים כל ערך, אילו שגיאות יכולות לחזור ומה לעשות בכל מקרה.

> המסמך לא כולל קוד React. הוא מתאר **מה** לשלוח ו**מה** מקבלים, ואת כותבת בעצמך את הקוד שעושה את זה.

## 1. כתובת השרת

| סביבה | Base URL |
|---|---|
| במחשב שלך | `http://localhost:3000` |
| בענן (Render) | `https://<שם-השירות-שלך>.onrender.com` |

כל ה־Endpoints מתחילים ב־`/api`. למשל: `http://localhost:3000/api/events`.

**המלצה:** שמרי את ה־Base URL במשתנה סביבה של Vite (למשל `VITE_API_URL` בקובץ `.env` של פרויקט ה־React), כדי שתוכלי להחליף בין המחשב לענן בלי לשנות קוד.

**חשוב לגבי CORS:** השרת מאשר בקשות רק מכתובות שמוגדרות במשתנה `CORS_ORIGIN` של השרת. בברירת מחדל מאושר `http://localhost:5173` (הפורט של Vite). כשתעלי את ה־React לאינטרנט, הוסיפי את הכתובת שלו ל־`CORS_ORIGIN` ב־Render.

**שימי לב לגבי Render חינמי:** אם אין פניות לשרת 15 דקות, הוא "נרדם". הבקשה הראשונה אחרי זה יכולה לקחת עד כדקה. זה תקין – כדאי להציג מצב טעינה.

## 2. התחברות ו־Token

### איך זה עובד

1. המשתמשת נרשמת (`POST /api/auth/register`) או מתחברת (`POST /api/auth/login`).
2. השרת מחזיר `token` (מחרוזת ארוכה) ואת פרטי המשתמש `user`.
3. את שומרת את ה־token (למשל ב־`localStorage`), כדי שההתחברות תישאר גם אחרי רענון.
4. **בכל בקשה אחרת** את שולחת כותרת (Header):

```
Authorization: Bearer <ה-token>
```

שימי לב: המילה `Bearer`, רווח אחד, ואז ה־token.

### מתי ה־Token מפסיק לעבוד

- תוקף ה־token הוא **7 ימים**.
- כשהתוקף פג, או שה־token לא תקין, כל בקשה תחזיר **401**.
- **מה לעשות ב־401:** למחוק את ה־token השמור ולהעביר למסך התחברות.

### בדיקה בטעינת האפליקציה

כשהאפליקציה נפתחת ויש token שמור, קראי ל־`GET /api/auth/me`:
- **200** → המשתמשת מחוברת, ו־`data.user` מכיל את פרטיה.
- **401** → ה־token לא בתוקף. מחקי אותו ועברי להתחברות.

### התנתקות

אין Endpoint להתנתקות. פשוט מוחקים את ה־token מהדפדפן.

### חשוב לדעת

השרת קובע **מי את** אך ורק לפי ה־token. אין צורך (ואין טעם) לשלוח `userId` של המשתמשת המחוברת בשום בקשה.

## 3. כללים כלליים לכל הבקשות

| נושא | כלל |
|---|---|
| פורמט | כל הבקשות והתשובות ב־JSON. בבקשות עם גוף (POST / PUT) שלחי כותרת `Content-Type: application/json`. |
| תאריכים שמגיעים מהשרת | טקסט בפורמט ISO, למשל `"2026-12-15T18:00:00.000Z"`. ה־`Z` אומר שזה זמן UTC. כדי להציג בשעון ישראל, המירי לאובייקט `Date` והציגי בתצוגה מקומית. |
| תאריכים ששולחים לשרת | גם בפורמט ISO **עם אזור זמן**. אם יש לך תאריך ושעה מטופס, צרי מהם `Date` והמירי ל־ISO לפני השליחה. |
| כסף | מספרים רגילים (לא טקסט), עד 2 ספרות אחרי הנקודה. למשל `120.5`. |
| שדות ריקים | שדה רשות שאין בו ערך מגיע כ־`null` (לא כמחרוזת ריקה). |
| עדכון חלקי (PUT) | שולחים **רק** את השדות שמשתנים. כדי לרוקן שדה רשות, שולחים אותו עם `null`. |
| שדות לא מוכרים | שדה שהשרת לא מכיר גורם לשגיאת 400. שלחי רק את השדות שמופיעים במדריך. |
| מזהים בכתובת | `:eventId`, `:taskId` וכו' הם מספרים. מזהה לא מספרי → 400. |
| מחיקה | מחיקה מחזירה 200 עם `{ "message": "..." }` (לא 204), כך שתמיד אפשר לקרוא JSON מהתשובה. |

## 4. שגיאות וקודי סטטוס

### פורמט אחיד לכל שגיאה

```json
{
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "הנתונים שנשלחו אינם תקינים",
    "details": [
      { "field": "title", "message": "נדרשים לפחות 2 תווים" }
    ]
  }
}
```

| מה רוצים | איך קוראים |
|---|---|
| הודעה כללית להצגה | `data.error.message` (כבר בעברית) |
| קוד קבוע לבדיקה בקוד | `data.error.code` |
| שגיאה בשדה מסוים בטופס | עוברים על `data.error.details`. בכל פריט: `field` (שם השדה) ו־`message` (מה לא תקין) |

בשדות בתוך רשימות, `field` נראה כך: `invitees.2.email` (המוזמן השלישי ברשימה, שדה email) או `questions.0.options` (השאלה הראשונה).

### קודי סטטוס

| קוד | משמעות | מה לעשות בצד הלקוח |
|---|---|---|
| 200 | הצלחה | להציג את התוצאה |
| 201 | נוצר בהצלחה | להציג הודעת הצלחה / לעבור למסך הבא |
| 400 | נתונים לא תקינים | להציג שגיאה ליד כל שדה לפי `details` |
| 401 | לא מחוברת / Token לא בתוקף | למחוק token ולעבור להתחברות. **חריג:** ב־login, 401 פירושו מייל או סיסמה שגויים – פשוט להציג הודעה |
| 403 | אין הרשאה (למשל משתתפת שמנסה פעולה של מארגן) | להציג `message`. כדאי גם לא להציג את הכפתור מראש (לפי `myRole` / `isMine`) |
| 404 | לא נמצא, **או שאינך חברה במפגש** | להציג "המפגש לא נמצא" ולחזור לרשימה |
| 409 | התנגשות (למשל תפקיד שכבר נלקח) | להציג `message` ולרענן את הנתונים |
| 413 | בקשה גדולה מדי | לא אמור לקרות בשימוש רגיל |
| 500 | שגיאה בשרת | להציג "אירעה שגיאה, נסי שוב" |
| 503 | אין חיבור למסד הנתונים (רק ב־health) | – |

### קטלוג קודי שגיאה (`error.code`)

| קוד | סטטוס | מתי |
|---|---|---|
| `VALIDATION_ERROR` | 400 | שדה חסר / לא תקין |
| `INVALID_JSON` | 400 | גוף הבקשה אינו JSON תקין |
| `WRONG_PASSWORD` | 400 | שינוי סיסמה: הסיסמה הנוכחית שגויה |

| `TOKEN_INVALID` | 401 | Token לא תקין, או שהמשתמש לא קיים |
| `TOKEN_EXPIRED` | 401 | פג תוקף ה־Token |
| `INVALID_CREDENTIALS` | 401 | מייל או סיסמה שגויים בהתחברות |
| `ORGANIZER_ONLY` | 403 | פעולה של מארגן בלבד |
| `ORGANIZER_CANNOT_LEAVE` | 403 | מארגן ניסה לעזוב את המפגש שלו |
| `NOT_YOUR_TASK` | 403 | ניסיון לשחרר תפקיד של מישהו אחר |

| `TASK_NOT_FOUND` / `EXPENSE_NOT_FOUND` | 404 | התפקיד / ההוצאה לא נמצאו במפגש |

| `EMAIL_TAKEN` / `PHONE_TAKEN` | 409 | המייל / הטלפון כבר רשומים |

| `HAS_EXPENSES` | 409 | עזיבה / הסרה של משתתף שרשם הוצאות |
| `TASK_TAKEN` | 409 | עריכה / מחיקה של תפקיד שכבר נלקח |
| `TASK_ALREADY_TAKEN` | 409 | ניסיון לקחת תפקיד שמישהו אחר לקח |
| `TASK_ALREADY_MINE` | 409 | ניסיון לקחת תפקיד שכבר שלך |
| `TASK_NOT_TAKEN` | 409 | ניסיון לשחרר תפקיד פנוי |
| `SURVEY_CLOSED` | 409 | מענה / הוספת שאלה כשהמפגש כבר לא "בתכנון" |
| `DUPLICATE` | 409 | ערך כפול (מקרה נדיר של שתי בקשות בו־זמנית) |
| `INTERNAL_ERROR` | 500 | שגיאה לא צפויה בשרת |

## 5. ערכי שדות בחירה ותרגום לעברית

השרת שולח ומקבל ערכים באנגלית. את מציגה את התרגום בעברית.

**קטגוריה – `category`**

| ערך | להצגה |
|---|---|
| `FAMILY` | משפחתי |
| `FRIENDS` | חברים |
| `CLASS_COMMUNITY` | כיתה / קהילה |
| `WORK` | עבודה |
| `OTHER` | אחר |

**סוג פעילות – `activityType`**

| ערך | להצגה |
|---|---|
| `BIRTHDAY` | יום הולדת |
| `GATHERING` | מפגש |
| `MEAL` | ארוחה |
| `SPORT` | ספורט |
| `TRIP` | טיול |
| `REFRESHMENT` | התרעננות |
| `HOLIDAY` | חג |
| `OTHER` | אחר |

**סטטוס – `status`**

| ערך | להצגה | משמעות |
|---|---|---|
| `PLANNING` | בתכנון | ברירת מחדל. הסקר פתוח למענה |
| `SCHEDULED` | נקבע | הפרטים סגורים. הסקר נסגר |
| `COMPLETED` | הסתיים | המפגש עבר. ההתחשבנות עדיין זמינה |
| `CANCELLED` | בוטל | – |

**תפקיד במפגש – `myRole` / `role`**: `ORGANIZER` = מארגן, `PARTICIPANT` = משתתף.

**סטטוס הזמנה**: `PENDING` = ממתינה, `ACCEPTED` = אושרה, `DECLINED` = נדחתה.

## 8. פירוט מלא של כל Endpoint

בדוגמאות, `data` הוא תוכן התשובה (ה־JSON) אחרי שקראת אותו.

### מערכת

#### #1 · `GET /api/health` – בדיקת בריאות

- **למה:** לבדוק שהשרת עובד ומחובר למסד הנתונים. שימושי גם כדי "להעיר" את השרת ב־Render.
- **הרשאה:** ציבורי.
- **תשובה 200:**
```json
{ "status": "ok", "database": "up", "time": "2026-10-19T08:00:00.000Z" }
```
- **503:** `status: "error"`, `database: "down"` – אין חיבור למסד.
- **בצד הלקוח:** לא חובה להשתמש. אפשר לקרוא אליו בטעינת האפליקציה ולהציג "מתחבר לשרת..." עד שחוזרת תשובה.

### התחברות ופרופיל

#### #2 · `POST /api/auth/register` – הרשמה

- **למה:** יצירת חשבון. המשתמשת מחוברת מיד אחרי ההרשמה.
- **דרישה:** התחברות.
- **הרשאה:** ציבורי.
- **גוף הבקשה (כל השדות חובה):**

| שדה | כללים |
|---|---|
| `fullName` | 2–80 תווים |
| `email` | מייל תקין. נשמר באותיות קטנות |
| `phone` | טלפון ישראלי. אפשר עם מקפים או `+972`; נשמר כספרות בלבד, למשל `0501234567` |
| `password` | 8–72 תווים, לפחות אות אחת באנגלית ולפחות ספרה אחת |

```json
{ "fullName": "רחל לוי", "email": "rachel@example.com", "phone": "050-123-4567", "password": "Secret123" }
```
- **תשובה 201:**
```json
{
  "token": "eyJhbGciOi...",
  "user": { "id": 1, "fullName": "רחל לוי", "email": "rachel@example.com", "phone": "0501234567",
            "createdAt": "...", "updatedAt": "..." }
}
```
- **קריאת הערכים:** ה־token: `data.token`. שם להצגה: `data.user.fullName`.
- **שגיאות:** 400 (שדות לא תקינים, עם `details` לכל שדה), 409 `EMAIL_TAKEN` / `PHONE_TAKEN`.
- **בצד הלקוח:** אחרי 201 – לשמור את ה־token ואת `user`, ולעבור לדף הבית. בשגיאת 409 להציג את ההודעה ליד שדה המייל או הטלפון.

#### #3 · `POST /api/auth/login` – התחברות

- **למה:** קבלת token למשתמש קיים.
- **דרישה:** התחברות.
- **הרשאה:** ציבורי.
- **גוף:** `email`, `password` (שניהם חובה).
- **תשובה 200:** בדיוק כמו בהרשמה: `{ token, user }`.
- **שגיאות:** 400 (שדה ריק), 401 `INVALID_CREDENTIALS` – "מייל או סיסמה שגויים".
- **בצד הלקוח:** ב־401 כאן **לא** מנתקים – פשוט מציגים את ההודעה מתחת לטופס.

#### #4 · `GET /api/auth/me` – המשתמש המחובר

- **למה:** לבדוק שה־token בתוקף ולקבל פרטים עדכניים (למשל במסך הפרופיל).
- **הרשאה:** 🔐.
- **תשובה 200:** `{ "user": { id, fullName, email, phone, createdAt, updatedAt } }`.
- **קריאה:** `data.user.email`.

#### #5 · `PUT /api/users/me` – עריכת הפרופיל שלי

- **למה:** שינוי שם, מייל או טלפון.
- **דרישה:** עריכת רשומה.
- **הרשאה:** 🔐 – תמיד רק הפרופיל של המשתמשת המחוברת.
- **גוף:** לפחות אחד מ־`fullName`, `email`, `phone` (אותם כללים כמו בהרשמה).
```json
{ "fullName": "רחל לוי-כהן", "phone": "0509998877" }
```
- **תשובה 200:** `{ "user": { ... } }` עם הערכים המעודכנים.
- **שגיאות:** 400, 409 `EMAIL_TAKEN` / `PHONE_TAKEN`.
- **בצד הלקוח:** אחרי 200 לעדכן את פרטי המשתמש השמורים אצלך. **שימי לב:** אם המייל או הטלפון השתנו, ההזמנות שהמשתמשת תראה ב"ההזמנות שלי" יהיו לפי הפרטים החדשים.

#### #6 · `PUT /api/users/me/password` – שינוי סיסמה

- **הרשאה:** 🔐.
- **גוף (חובה):** `currentPassword`, `newPassword` (אותם כללים כמו סיסמה בהרשמה).
- **תשובה 200:** `{ "message": "הסיסמה עודכנה בהצלחה" }`.
- **שגיאות:** 400 `WRONG_PASSWORD` (עם `details[0].field = "currentPassword"`), 400 `VALIDATION_ERROR` לסיסמה חדשה חלשה.
- **בצד הלקוח:** ה־token הקיים ממשיך לעבוד, אין צורך להתחבר מחדש.

#### #7 · `GET /api/home` – נתוני דף הבית

- **למה:** כל המידע של דף הבית בקריאה אחת.
- **הרשאה:** 🔐.
- **תשובה 200:**
```json
{
  "user": { "id": 2, "fullName": "שרה כהן" },
  "upcomingEvents": [
    { "id": 12, "title": "ארוחת חנוכה", "eventDate": "2026-12-15T18:00:00.000Z", "location": "בית סבא",
      "status": "SCHEDULED", "category": "FAMILY", "activityType": "MEAL", "myRole": "PARTICIPANT" }

    { "id": 5, "description": "להביא שתייה", "event": { "id": 12, "title": "ארוחת חנוכה", "eventDate": "..." } }
```

|---|---|
| "שלום, שרה" | `data.user.fullName` |
| עד 5 מפגשים קרובים | `data.upcomingEvents` (ממוינים מהקרוב ביותר; מפגשים בלי תאריך בסוף) |

### מפגשים

#### #8 · `GET /api/events` – המפגשים שלי

- **למה:** רשימת כל המפגשים שאני מארגנת או משתתפת בהם, עם חיפוש, סינון ומיון.
- **דרישה:** רשימת רשומות; חיפוש, סינון ומיון; שדה בחירה.
- **הרשאה:** 🔐. מוחזרים **רק** מפגשים שאני חברה בהם.
- **בלי פרמטרים בכלל** → מוחזרים **כל** המפגשים שלי, ממוינים לפי תאריך המפגש מהמוקדם למאוחר (מפגשים בלי תאריך בסוף). אין חלוקה לעמודים.
- **פרמטרים (כולם רשות, אפשר לשלב כמה):**

| פרמטר | ערכים | מה עושה |
|---|---|---|
| `search` | טקסט | מחפש בשם המפגש (חלק מהשם מספיק) |
| `category` | `FAMILY` ... | רק בקטגוריה הזו |
| `activityType` | `BIRTHDAY` ... | רק בסוג הפעילות הזה |
| `status` | `PLANNING` ... | רק בסטטוס הזה |
| `myRole` | `ORGANIZER` / `PARTICIPANT` | רק מפגשים שאני מארגנת / משתתפת |
| `timeframe` | `upcoming` / `past` / `all` | `upcoming` = בתכנון או נקבע, ותאריך שעוד לא עבר (או שאין תאריך). `past` = כל השאר. ברירת מחדל `all` |
| `sortBy` | `eventDate` / `createdAt` | לפי תאריך המפגש / תאריך היצירה. ברירת מחדל `eventDate` |
| `sortOrder` | `asc` / `desc` | עולה / יורד. ברירת מחדל `asc` |

**דוגמאות:**
- הכל: `/api/events`
- "מהמאוחר למוקדם": `/api/events?sortBy=eventDate&sortOrder=desc`
- "אירועים שאני מארגנת": `/api/events?myRole=ORGANIZER`
- שילוב: `/api/events?search=חנוכה&category=FAMILY&timeframe=upcoming`

**איך בונים את הכתובת:** מוסיפים לכתובת `?` ואז זוגות `שם=ערך` מופרדים ב־`&`. פרמטר שאין לו ערך – לא שולחים בכלל (לא לשלוח `category=` ריק). טקסט חיפוש בעברית צריך קידוד לכתובת (URL encoding) – הדפדפן עושה זאת אם בונים את הכתובת עם `URLSearchParams`.

- **תשובה 200:**
```json
{
  "count": 1,
  "events": [
    { "id": 12, "title": "ארוחת חנוכה", "description": null, "category": "FAMILY", "activityType": "MEAL",
      "status": "SCHEDULED", "eventDate": "2026-12-15T18:00:00.000Z", "location": "בית סבא",
      "myRole": "ORGANIZER", "participantsCount": 6,
      "organizer": { "id": 1, "fullName": "רחל לוי" }, "createdAt": "..." }
  ]
}
```
- **קריאה:** מספר תוצאות `data.count`; לעבור על `data.events`; התפקיד שלי `data.events[i].myRole`; "אין עדיין תאריך" כש־`eventDate` הוא `null`.
- **שגיאות:** 400 – ערך לא מוכר באחד הפרמטרים (למשל `category=ABC`).
- **בצד הלקוח:** כשמשנים חיפוש / סינון / מיון – קוראים שוב עם הפרמטרים החדשים. בחיפוש מומלץ לחכות שהמשתמשת תפסיק להקליד (debounce) לפני השליחה.

#### #9 · `POST /api/events` – יצירת מפגש (אשף)

- **למה:** יצירת מפגש חדש, יחד עם רשימת המוזמנים ושאלות הסקר, **בקריאה אחת** בסוף האשף.
- **דרישה:** הוספת רשומה; אובייקט מרכזי; שדה בחירה.
- **הרשאה:** 🔐 – כל משתמש. היוצר הופך אוטומטית למארגן.
- **גוף הבקשה:**

| שדה | חובה | כללים |
|---|---|---|
| `title` | ✅ | 2–100 תווים |
| `description` | | עד 1000 תווים, או `null` |
| `eventDate` | | ISO עם אזור זמן, או `null` |
| `location` | | עד 200 תווים |
| `food` | | עד 500 תווים |
| `category` | | ברירת מחדל `OTHER` |
| `activityType` | | ברירת מחדל `OTHER` |
| `status` | | ברירת מחדל `PLANNING` |
| `budget` | | 0 עד 1,000,000, או `null` |
| `invitees` | | רשימה (עד 100). כל פריט: `{ "email": "..." }` או `{ "phone": "..." }` או `{ "contact": "..." }` |
| `questions` | | רשימה (עד 30). כל פריט: `{ "text": "...", "options": ["...", "..."] }` עם 2–10 תשובות שונות |

**על `contact`:** בשלב המשתתפים יש שדה אחד "טלפון או מייל". שלחי את מה שהוקלד בשדה `contact`, והשרת יזהה לבד אם זה מייל (יש `@`) או טלפון. שורות ריקות – לא לשלוח.

```json
{
  "title": "ארוחת חנוכה משפחתית",
  "description": "מפגש משפחתי שנתי",
  "category": "FAMILY",
  "activityType": "MEAL",
  "budget": 800,
  "invitees": [ { "contact": "sara@example.com" }, { "contact": "052-111-2233" } ],
  "questions": [
    { "text": "איפה נוח לכם?", "options": ["בית סבא", "פארק"] },
    { "text": "מה תעדיפו לאכול?", "options": ["חלבי", "בשרי"] }
  ]
}
```
- **תשובה 201:** דף המפגש המלא (כמו ב־#10), ובנוסף:
```json
{
  "event": { "...": "..." },
  "participants": [ { "...": "המארגן" } ],
  "tasks": [],
  "invitationsSummary": { "createdCount": 2, "skippedCount": 0, "skipped": [] },
  "questionsCount": 2
}
```
- **קריאה:** מזהה המפגש החדש `data.event.id`. כמה הזמנות נשלחו `data.invitationsSummary.createdCount`. מוזמנים שדולגו `data.invitationsSummary.skipped` – בכל אחד `email` / `phone`, `reason` ו־`message` להצגה.
  - `reason` יכול להיות: `DUPLICATE_IN_LIST` (הופיע פעמיים ברשימה), `ALREADY_PARTICIPANT` (למשל המארגן עצמו), `ALREADY_INVITED`.
- **שגיאות:** 400 – למשל `details[0].field = "invitees.1.contact"` (המוזמן השני לא תקין) או `"questions.0.options"`. **אם יש שגיאה – שום דבר לא נשמר**, כך שאפשר לתקן ולשלוח שוב.
- **בצד הלקוח:** שמרי את נתוני שלושת שלבי האשף אצלך, ושלחי רק בלחיצה על "סיום". כדי להחזיר את המשתמשת לשלב הנכון בשגיאה, בדקי במה מתחיל `field`: `invitees` → שלב המשתתפים, `questions` → שלב הסקר, אחרת → שלב הפרטים. אחרי 201 – לעבור לדף המפגש החדש.

#### #10 · `GET /api/events/:eventId` – דף מפגש

- **למה:** כל פרטי המפגש, המשתתפים המאושרים והתפקידים.
- **דרישה:** אובייקט מרכזי; הרשאות.
- **הרשאה:** 🔐 חבר במפגש.
- **תשובה 200:**
```json
{
  "event": {
    "id": 12, "title": "ארוחת חנוכה", "description": "...", "eventDate": null, "location": null,
    "food": "לביבות", "category": "FAMILY", "activityType": "MEAL", "status": "PLANNING", "budget": 800,
    "organizer": { "id": 1, "fullName": "רחל לוי", "phone": "0501234567" },
    "myRole": "ORGANIZER", "createdAt": "...", "updatedAt": "..."
  },
  "participants": [
    { "userId": 1, "fullName": "רחל לוי", "phone": "0501234567", "role": "ORGANIZER", "joinedAt": "..." }
  ],
  "tasks": [
    { "id": 5, "description": "להביא שתייה", "isTaken": true,
      "assignee": { "id": 3, "fullName": "שרה כהן" }, "isMine": false, "createdAt": "..." },
    { "id": 6, "description": "לקנות כלים", "isTaken": false, "assignee": null, "isMine": false, "createdAt": "..." }
  ]
}
```
- **קריאה:**

| מה | איפה |
|---|---|
| שם המפגש | `data.event.title` |
| האם אני המארגן | `data.event.myRole === "ORGANIZER"` |
| טלפון המארגן | `data.event.organizer.phone` |
| רשימת משתתפים (רק מאושרים) | `data.participants` – המארגן תמיד ראשון |
| מי לקח תפקיד | `data.tasks[i].assignee.fullName` (אם `isTaken`) |
| תפקיד פנוי | `data.tasks[i].isTaken === false` |
| תפקיד שלי | `data.tasks[i].isMine === true` |

- **שגיאות:** 404 `EVENT_NOT_FOUND` – המפגש לא קיים **או** שאינך חברה בו (כולל מי שהוזמנה ועוד לא אישרה). 400 – מזהה לא מספרי.
- **בצד הלקוח:** הסקר וההוצאות **לא** נמצאים כאן – כל לשונית טוענת את שלה (#27, #31).

#### #11 · `PUT /api/events/:eventId` – עריכת מפגש

- **למה:** עדכון פרטים (למשל לפי תוצאות הסקר) ושינוי סטטוס.
- **דרישה:** עריכת רשומה; הרשאות; שדה בחירה.
- **הרשאה:** 🔐 מארגן בלבד.
- **גוף:** כל שדה מ־#9 **חוץ מ־`invitees` ו־`questions`**. עדכון חלקי – לפחות שדה אחד. `null` מרוקן שדה רשות.
```json

  "participantsCount": 6,
  "respondentsCount": 4,
  "responseRate": 66.7,
  "questions": [
    { "id": 1, "text": "איפה נוח לכם?", "order": 1, "respondentsCount": 4,

        { "id": 10, "text": "בית סבא", "votes": 3, "percentage": 75, "isTop": true,
```

**ג. הטבלה המפורטת (משתתף ← תשובות):**
- **שורות:** כל פריט ב־`data.responses`. שם: `user.fullName`.
- **עמודות:** כל פריט ב־`data.questions`. כותרת: `text`.
- **תא:** בתוך `answers` של השורה – הפריט עם אותו `questionId` כמו ה־`id` של העמודה (הם באותו סדר כמו `questions`). מציגים את `optionTexts` מחוברים בפסיק. רשימה ריקה = לא סימן כלום בשאלה הזו.
- **עמודה אחרונה:** `note` (או ריק אם `null`).

**ד. מי עוד לא ענה:** `data.notResponded`.

- **בצד הלקוח:** מתחת לתוצאות אפשר לשים כפתור "קביעת פרטים" שפותח את עריכת המפגש (#11), וכדאי להציע מעבר לסטטוס "נקבע".

- **תשובה 201:** `{ "expense": { ... } }`.
- **שגיאות:** 400.
- **בצד הלקוח:** ערך משדה קלט מגיע כטקסט – המירי למספר לפני השליחה. אחרי 201 – לרענן את #31 (כי הסיכומים משתנים).

#### #33 · `PUT /api/events/:eventId/expenses/:expenseId` – עריכת הוצאה שלי

- **הרשאה:** 🔐 רק מי שרשם את ההוצאה.
- **גוף:** `amount` ו/או `reason`.
- **תשובה 200:** `{ "expense": { ... } }`.
- **שגיאות:** 400, 403 `NOT_YOUR_EXPENSE`, 404 `EXPENSE_NOT_FOUND`.

#### #34 · `DELETE /api/events/:eventId/expenses/:expenseId` – מחיקת הוצאה שלי

- **הרשאה:** 🔐 רק מי שרשם את ההוצאה (גם המארגן מוחק רק את שלו).
- **תשובה 200:** `{ "message": "ההוצאה נמחקה" }`.
- **שגיאות:** 403 `NOT_YOUR_EXPENSE`, 404.

**חשוב:** כל רישום, עריכה או מחיקה של הוצאה (וגם הצטרפות / עזיבה של משתתף) מסמנים את ההתחשבנות האחרונה כ"לא מעודכנת" (`isOutdated: true` ב־#36).

#### #35 · `POST /api/events/:eventId/settlement/calculate` – חישוב התחשבנות

- **למה:** הכפתור "חישוב התחשבנות" של המארגן.
- **הרשאה:** 🔐 מארגן בלבד.
- **גוף:** אין.
- **איך מחושב:** סך כל ההוצאות מחולק **שווה בשווה** בין **כל** משתתפי המפגש (כולל המארגן). אם הסכום לא מתחלק בדיוק, האגורות העודפות מתחלקות אחת־אחת. השרת יוצר רשימת העברות קצרה ככל האפשר. חישוב חדש מחליף את הקודם.
- **תשובה 200:** בדיוק אותו מבנה כמו #36.
- **שגיאות:** 403, 404.

#### #36 · `GET /api/events/:eventId/settlement` – תוצאת ההתחשבנות

- **הרשאה:** 🔐 חבר – כולם רואים את התוצאה.
- **תשובה 200:**
```json
{
  "calculated": true,
  "calculatedAt": "2026-11-02T18:30:00.000Z",
  "isOutdated": false,
  "total": 600,
  "participantsCount": 3,
  "sharePerPerson": 200,
  "myBalance": -200,
  "balances": [
    { "userId": 1, "fullName": "רחל לוי", "paid": 400, "share": 200, "balance": 200 },
    { "userId": 2, "fullName": "שרה כהן", "paid": 200, "share": 200, "balance": 0 },
    { "userId": 3, "fullName": "דנה", "paid": 0, "share": 200, "balance": -200 }
  ],
  "transfers": [
    { "id": 1, "from": { "id": 3, "fullName": "דנה", "phone": "0533334444" },
               "to":   { "id": 1, "fullName": "רחל לוי", "phone": "0501234567" }, "amount": 200 }
  ],
  "myTransfers": {
    "toPay": [ { "id": 1, "toUser": { "id": 1, "fullName": "רחל לוי", "phone": "0501234567" }, "amount": 200 } ],
    "toReceive": []
  }
}
```
- **קריאה:**

| מה | איפה |
|---|---|
| כבר חושב? | `data.calculated`. אם `false` – כל השדות `null` והרשימות ריקות; להציג "ההתחשבנות עוד לא חושבה" |
| מתי | `data.calculatedAt` |
| התוצאה ישנה? | `data.isOutdated` – להציג "היו שינויים מאז החישוב", ולמארגן להציע לחשב שוב |
| סך הכל וחלק לאדם | `data.total`, `data.sharePerPerson` |
| המצב שלי | `data.myBalance`: חיובי = מגיע לי, שלילי = אני חייבת, 0 = מאוזנת. `null` אם הצטרפתי אחרי החישוב |
| טבלה לכל משתתף | `data.balances`: שילם (`paid`), החלק שלו (`share`), יתרה (`balance`) |
| כל ההעברות | `data.transfers`: "**from** מעביר ל־**to** סכום **amount**", כולל טלפונים |
| כמה אני משלמת ולמי | `data.myTransfers.toPay` – `toUser.fullName`, `toUser.phone`, `amount` |
| ממי אני מקבלת | `data.myTransfers.toReceive` – `fromUser`, `amount` |

## 9. תהליכים מלאים צעד אחר צעד

### א. הרשמה והתחברות
1. טופס הרשמה → #2. בהצלחה: שומרים `token` ו־`user`, עוברים לדף הבית.
2. בכל טעינה של האפליקציה עם token שמור → #4. ב־401 מוחקים ומעבירים להתחברות.
3. בכל בקשה מוסיפים `Authorization: Bearer <token>`. בכל 401 (חוץ מבטופס ההתחברות) → מנתקים.

### ב. אשף יצירת מפגש
1. **שלב 1 – פרטים:** טופס עם `title` (חובה) ושאר השדות (רשות). "המשך" רק אם יש שם (2 תווים לפחות). שומרים אצלך, **לא שולחים עדיין**.
2. **שלב 2 – משתתפים:** רשימת שדות "טלפון או מייל" עם כפתור +. שומרים אצלך. שורות ריקות לא נכנסות.
3. **שלב 3 – סקר:** אפשר לטעון את #37 כנקודת התחלה. בכל שאלה: טקסט + רשימת תשובות עם +, ולמטה + להוספת שאלה. ודאי שלכל שאלה יש לפחות 2 תשובות.
4. **"סיום":** בונים גוף אחד לפי #9: שדות שלב 1 + `invitees` (כל שורה כ־`{ contact: ... }`) + `questions`. שולחים #9.
5. **201:** מציגים כמה הזמנות נשלחו (ואת המדולגים אם יש), ועוברים לדף המפגש `data.event.id`.
6. **400:** לפי `details[0].field` חוזרים לשלב המתאים ומציגים את ההודעות.

> **הערה על "שדה חופשי בסוף הסקר":** הוא לא שאלה שהמארגן יוצר. הוא קיים אוטומטית בכל סקר – שדה `note` ב־#29, וכל משתתף רואה אותו בסוף הטופס.

### ג. מוזמן מקבל הזמנה
1. דף הבית (#7) מציג `pendingInvitationsCount`.
2. מסך "ההזמנות שלי" (#18) – כרטיס לכל הזמנה עם פרטי המפגש.
3. "אישור" → #19 → ניווט לדף המפגש עם `eventId`. "דחייה" → #20 → הכרטיס נעלם.
4. מי שעוד לא רשום: נרשם עם אותו מייל / טלפון שהוזמן אליו, ומיד רואה את ההזמנה ב־#18.

### ד. סקר ← קביעת פרטים
1. משתתף נכנס ללשונית הסקר → #27 → מסמן ושולח #29 (אפשר לחזור ולערוך כל עוד `isOpen`).
2. המארגן → #30 → רואה סטטיסטיקות וטבלה.
3. המארגן קובע פרטים → #11 עם `eventDate`, `location`, `food` ו־`status: "SCHEDULED"`. הסקר נסגר.

### ה. תפקידים
1. המארגן יוצר תפקידים (#22).
2. כל משתתף לוקח תפקיד פנוי (#25). ב־409 – לרענן (#21).
3. מי שלקח יכול לוותר (#26).

### ו. הוצאות והתחשבנות
1. כל משתתף רושם את ההוצאות שלו (#32) ורואה את המצב מול התקציב (#31).
2. המארגן לוחץ "חישוב התחשבנות" (#35).
3. כולם רואים מי מעביר כמה ולמי (#36). כל משתתף רואה בדף הבית כמה עליו לשלם (#7).
4. אם נוספה הוצאה אחרי החישוב → `isOutdated: true` → המארגן מחשב שוב.
